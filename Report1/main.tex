\section*{Abstract}

\noindent\textbf{Project (Topic 6):} \textsc{Boolean Network Analyzer} -- a software tool for parsing, simulating and visualising Boolean Networks.

\vspace{0.4em}

A Boolean Network (BN) is a discrete mathematical model originally proposed by Stuart Kauffman in 1969 to study \textit{gene regulatory networks}. Each node in the network carries one of two values $\{0, 1\}$ and is updated by a Boolean function of its neighbours' states. In spite of its very simple representation, a Boolean Network is expressive enough to describe \textit{steady states}, \textit{cyclic oscillations} and \textit{complex} behaviours of real biological and industrial logic systems. Tools such as \textsc{GINsim}, \textsc{PyBoolNet}, \textsc{BoolNet} (R) and \textsc{CellNetAnalyzer} have become de facto international standards for BN dynamics research.

\vspace{0.3em}

This report documents the \textit{theoretical study, architectural design, implementation and evaluation} of a complete \textsc{Boolean Network Analyzer} delivered as a zero-install, in-browser web application hosted on GitHub Pages\footnote{Source: \url{https://github.com/dangkhoi-dev/boolean-network-analyzer}. Live demo: \url{https://dangkhoi-dev.github.io/boolean-network-analyzer/}}. The software supports five mandatory feature blocks: (i) a \textbf{Parser} that reads the standard \texttt{.bnet} format (compatible with PyBoolNet) consisting of update rules of the form \texttt{target, expression}; (ii) an \textbf{Influence Graph Builder} that constructs the signed influence graph (+/--/?), with the sign inferred from a monotonicity test on the Boolean function; (iii) a \textbf{State Transition Graph (STG) Engine} that enumerates the entire $2^n$ state space under the two canonical update schemes -- \textit{synchronous} and \textit{asynchronous}; (iv) an \textbf{Attractor Finder} that applies strongly connected component (SCC) decomposition (Tarjan) on the condensation graph to identify every attractor and classify it as \textit{fixed-point}, \textit{cyclic} or \textit{complex}; (v) a \textbf{Visualiser} that produces interactive renderings of all graphs in the browser (using \texttt{vis-network}), with PNG export for reporting. The same algorithms are also exposed as a Python reference implementation used by the automated test suite.

\vspace{0.3em}

The project offers four main contributions: \textbf{(1) A clean modular architecture} (Parser $\rightarrow$ Network $\rightarrow$ STG $\rightarrow$ Attractors $\rightarrow$ Visualizer) that separates I/O from algorithmic logic, implemented twice in parallel (Python reference + vanilla-JavaScript in-browser engine) and cross-validated against each other; \textbf{(2) An automated test suite (pytest)} covering parser, network evaluation, STG, attractors and bundled samples; \textbf{(3) Cross-validation against the reference tool PyBoolNet} on five sample networks (\textit{toy switch}, \textit{bistable toggle}, \textit{repressilator}, \textit{fission yeast}, \textit{mammalian cell cycle}) -- the attractor results match 100\%; \textbf{(4) A friendly zero-install web frontend} for non-programmers: a single static HTML/JS page deployed via GitHub Pages, integrating file upload, sample selection, scheme switching, trajectory simulation and figure download with no backend or installation required.

\vspace{0.3em}

The software has been tested with five networks ranging from 2 to 10 nodes. In every case the attractor results agree with the original publications (Davidich \& Bornholdt 2008, Faure \emph{et al.} 2006, Gardner \emph{et al.} 2000). Performance evaluation shows that the software is responsive for networks with $\leq 16$ nodes (i.e.\ up to $2^{16}=65\,536$ states); beyond that threshold the cost of generating the full STG grows exponentially and the user is encouraged to switch to \textit{reachable-only} mode (BFS from a chosen initial state). All source code, sample dataset and documentation are organised according to a professional project layout (\texttt{src/}, \texttt{tests/}, \texttt{samples/}, \texttt{docs/}) and released on a public GitHub repository.

\vspace{0.3em}

\noindent\textbf{Keywords:} Boolean Network, Influence Graph, State Transition Graph, Attractor, Synchronous Update, Asynchronous Update, Strongly Connected Component, PyBoolNet, GitHub Pages, vis-network, Bioinformatics.

\subsection{Background}\label{subsec:background}

\subsubsection{Boolean Networks in systems science}
A Boolean Network (BN) is a class of discrete mathematical model used to describe the \textit{dynamics} of systems in which every component takes only one of two discrete values: \textit{on} (1, \texttt{True}, active) or \textit{off} (0, \texttt{False}, inactive). The model was introduced by Stuart A.\ Kauffman in 1969 \cite{kauffman1969metabolic} in the context of \textit{gene regulatory networks} (GRN). The core idea is the following: rather than modelling concentrations or reaction rates accurately by a system of ordinary differential equations (ODEs) -- which requires many hard-to-measure parameters -- each gene is \textit{abstracted} into a binary variable, and every regulatory relation is captured by a logical expression.

In spite of its very simple representation, Boolean Networks have proven to be a powerful tool capable of reproducing many qualitative phenomena observed in biology and engineering, including: the coexistence of multiple \textit{stable steady states} (multistability) that correspond to different cell phenotypes, \textit{periodic oscillations} in the cell cycle, \textit{robustness} against stochastic perturbations, and the existence of \textit{complex attractors} in asynchronously updated networks.

\subsubsection{Applications of Boolean Networks}
Today BNs are used not only in systems biology but in many other domains:

\begin{itemize}[leftmargin=*]
    \item \textbf{Molecular and medical biology}: Modelling cell cycles (\textit{S.\ pombe}, \textit{S.\ cerevisiae}, mammalian cell cycle), signalling networks (TGF-$\beta$, MAPK, T-cell receptor), apoptosis and viral infection dynamics \cite{faure2006,davidich2008,schwab2020}.
    \item \textbf{Digital logic circuit design}: Each gate is abstracted into a BN node; analysing the STG allows the detection of race conditions and glitches in combinational/sequential circuits.
    \item \textbf{Industrial PLC control systems}: Logical relations between sensors and actuators can be cast as a BN, enabling formal verification of safety properties.
    \item \textbf{Computational social science}: BNs are used to simulate \textit{opinion dynamics} on social networks, where each individual carries a 0/1 view that depends on their neighbours.
\end{itemize}

\subsubsection{Tooling gap and motivation}
Although professional tools such as \textsc{GINsim} \cite{naldi2009}, \textsc{PyBoolNet} \cite{klarner2017pyboolnet}, \textsc{BoolNet} (R) and \textsc{CellNetAnalyzer} are mature, they tend to have a \textit{high barrier of entry} for newcomers: GINsim requires a Java runtime and a fairly heavy Swing GUI; PyBoolNet is a pure-Python library without a visual frontend; BoolNet requires an R environment. For first/second-year students approaching the \textit{Programming Integration Project} module, having a \textit{lightweight, cross-platform web application} that allows uploading a \texttt{.bnet} file and immediately seeing the influence graph together with the attractors is highly valuable both for learning and for presenting results.

This is exactly the motivation behind our \textsc{Boolean Network Analyzer} -- a software with all the basic BN analysis features, accessible from \textit{any modern browser with zero installation} (the entire engine, including the SCC-based attractor finder, runs client-side in JavaScript), with the Python reference engine kept as a parallel implementation for testing and batch jobs, and the whole project organised in a professional layout that can be reused for future student projects. The live demo is hosted at \url{https://dangkhoi-dev.github.io/boolean-network-analyzer/} and the source code at \url{https://github.com/dangkhoi-dev/boolean-network-analyzer}.

The \textbf{Boolean Network Analyzer} project aims at building a software tool that can:

\section{Theoretical Background}\label{sec:theory}
%======================================================================

This section presents the mathematical concepts that underpin the Boolean Network Analyzer software. The exposition follows two primary sources: the survey paper by Schwab \emph{et al.} \cite{schwab2020} and the technical paper by Naldi \emph{et al.} \cite{naldi2009}. The definitions are reformulated in our own words with self-designed illustrative examples, in order to show genuine understanding rather than mechanical copying.

\subsection{Mathematical definition of a Boolean Network}\label{subsec:def-bn}

\subsubsection{Formal definition}

\begin{quote}
\textit{A Boolean Network on $n$ nodes is a triple}
$$\mathcal{B} = (V, \mathcal{F}, \mathcal{X})$$
\textit{where:}
\begin{itemize}[leftmargin=*]
    \item $V = \{v_1, v_2, \ldots, v_n\}$ is the set of $n$ \textit{nodes} (genes, variables, components).
    \item $\mathcal{X} = \{0, 1\}^n$ is the \textit{state space} of size $2^n$. A specific state $x = (x_1, x_2, \ldots, x_n) \in \mathcal{X}$ assigns a Boolean value to every node.
    \item $\mathcal{F} = \{f_1, f_2, \ldots, f_n\}$ is the set of \textit{update functions}, where $f_i : \{0,1\}^n \to \{0,1\}$ determines the next value of node $v_i$ based on the current state.
\end{itemize}
\end{quote}

In practice, $f_i$ usually depends only on a \textit{subset} of nodes $\mathrm{In}(v_i) \subseteq V$ -- the so-called \textit{regulator set} of $v_i$. The cardinality $|\mathrm{In}(v_i)|$ equals the \textit{in-degree} of $v_i$ in the influence graph (see \S\ref{subsec:influence-graph}).

\subsubsection{The \texttt{.bnet} rule format}

The \texttt{.bnet} format (used by BoolNet for R and by PyBoolNet) represents each rule on its own line according to the syntax:
\begin{lstlisting}[style=bnetStyle, caption={\texttt{.bnet} file syntax}, label={lst:bnet-syntax}]
# Comments start with '#' and run to end of line.
# Header (optional, ignored by the parser):
targets, factors
# One rule per line:
A, !B
B, A & !C
C, B | !A
\end{lstlisting}

The supported logical operators are \texttt{!} (NOT), \texttt{\&} (AND), \texttt{|} (OR) and parentheses. The constants \texttt{0, 1, True, False} are also recognised. Operator precedence follows the Python convention: NOT > AND > OR.

\subsubsection{Illustrative example: a 3-node \textit{toy switch}}

To make the discussion concrete, consider the 3-node \textit{toy switch} of Listing~\ref{lst:bnet-toy}:

\begin{lstlisting}[style=bnetStyle, caption={The 3-node \textit{toy switch} network}, label={lst:bnet-toy}]
targets, factors
A, !B
B, A & !C
C, B
\end{lstlisting}

Each node carries one rule:
\begin{align*}
f_A(x_A, x_B, x_C) &= \lnot x_B \\
f_B(x_A, x_B, x_C) &= x_A \land \lnot x_C \\
f_C(x_A, x_B, x_C) &= x_B
\end{align*}

The state space has $2^3 = 8$ states, numbered with binary strings \texttt{ABC}: \texttt{000, 001, 010, 011, 100, 101, 110, 111}. For example, from state $x = (1, 0, 0)$ ($A=1, B=0, C=0$) we compute:
\begin{align*}
f_A &= \lnot 0 = 1 \\
f_B &= 1 \land \lnot 0 = 1 \\
f_C &= 0
\end{align*}
Hence the next state (under the \textit{synchronous} scheme) is $(1, 1, 0)$. Repeating this for all eight states produces the complete STG (see \S\ref{subsec:stg}).

\subsection{The influence graph}\label{subsec:influence-graph}

\subsubsection{Definition}

\begin{quote}
\textit{The Influence Graph} $G_I = (V, E_I, \sigma)$ \textit{of a Boolean Network} $\mathcal{B}$ \textit{is a directed, signed graph in which:}
\begin{itemize}[leftmargin=*]
    \item The vertex set $V$ coincides with the node set of the BN.
    \item There is a directed edge $(u, v) \in E_I$ iff $u \in \mathrm{In}(v)$, that is, $u$ appears in the rule of $v$.
    \item $\sigma : E_I \to \{+, -, ?\}$ assigns a \textit{sign} to each edge:
    \begin{itemize}
        \item $\sigma(u,v) = +$ (activation) if turning $u$ on \textit{always} increases (or leaves unchanged) the value of $f_v$.
        \item $\sigma(u,v) = -$ (inhibition) if turning $u$ on \textit{always} decreases (or leaves unchanged) the value of $f_v$.
        \item $\sigma(u,v) = ?$ (non-monotonic) if the behaviour depends on the values of the other regulators.
    \end{itemize}
\end{itemize}
\end{quote}

\subsubsection{Inferring the edge sign}

Let $f_v$ be a rule and $u \in \mathrm{In}(v)$ one of its regulators. Write $\mathrm{In}(v) \setminus \{u\} = \{w_1, \ldots, w_k\}$. For every assignment $(b_1, \ldots, b_k) \in \{0,1\}^k$ of the remaining regulators we compute:
$$\Delta_u(b_1,\ldots,b_k) = f_v(u=1, b_1,\ldots,b_k) - f_v(u=0, b_1,\ldots,b_k) \in \{-1, 0, +1\}$$

Three cases arise:
\begin{itemize}[leftmargin=*]
    \item If $\Delta_u \geq 0$ for every $(b_1,\ldots,b_k)$ and $\Delta_u > 0$ at least once $\Rightarrow \sigma(u,v) = +$.
    \item If $\Delta_u \leq 0$ for every $(b_1,\ldots,b_k)$ and $\Delta_u < 0$ at least once $\Rightarrow \sigma(u,v) = -$.
    \item If both $\Delta_u > 0$ and $\Delta_u < 0$ occur for different assignments $\Rightarrow \sigma(u,v) = ?$.
\end{itemize}

This algorithm has complexity $O(2^{k})$ with $k = |\mathrm{In}(v)| - 1$. Because $k$ is small in practice (typically $\leq 5$ for biological networks), the sign inference is very fast.

\subsubsection{Worked example}

Applied to the \textit{toy switch}:
\begin{itemize}[leftmargin=*]
    \item Edge $B \to A$: $f_A = \lnot x_B$. When $B=0 \Rightarrow f_A = 1$; when $B=1 \Rightarrow f_A = 0$. Turning $B$ on always decreases $A$ $\Rightarrow$ sign \textbf{$-$}.
    \item Edge $A \to B$: $f_B = x_A \land \lnot x_C$. When $C=0$: $A=0 \Rightarrow f_B=0$; $A=1 \Rightarrow f_B=1$ (turning $A$ on increases $f_B$). When $C=1$: $A=0 \Rightarrow f_B=0$; $A=1 \Rightarrow f_B=0$ (unchanged). So $A$ is always $\geq$, with at least one strict increase $\Rightarrow$ sign \textbf{$+$}.
    \item Edge $C \to B$: $f_B = x_A \land \lnot x_C$. When $A=1$: $C=0 \Rightarrow f_B=1$; $C=1 \Rightarrow f_B=0$ (turning $C$ on decreases $f_B$). When $A=0$: $f_B=0$ for any $C$ (unchanged). $\Rightarrow$ sign \textbf{$-$}.
    \item Edge $B \to C$: $f_C = x_B$, strictly increasing in $B$ $\Rightarrow$ sign \textbf{$+$}.
\end{itemize}

    \centering
    \includegraphics[width=0.55\textwidth]{../docs/img/influence_toy.png}
    \caption{Influence graph of the 3-node \textit{toy switch}. Green edges denote activation (+); red edges denote inhibition (--).}
    \label{fig:influence-toy}

\subsubsection{Role of the influence graph}

The influence graph captures the \textit{topological} structure of the BN, independently of the precise form of the update functions. It is useful because:
\begin{itemize}[leftmargin=*]
    \item It \textbf{visualises} the regulatory structure quickly, with no need to run simulations.
    \item It exposes \textbf{feedback loops}: a closed loop with an even number of negative edges is a \textit{positive feedback} loop (usually associated with multistability); a loop with an odd number of negative edges is a \textit{negative feedback} loop (usually associated with oscillations).
    \item It allows \textbf{qualitative predictions} about the existence of attractors. According to Thomas's theorem \cite{thomas1981}, a network with multiple fixed-points requires at least one positive feedback loop, and a network with sustained oscillations requires at least one negative feedback loop.
\end{itemize}

\subsection{Update schemes: synchronous vs asynchronous}\label{subsec:update-schemes}

A key question when simulating a BN is: \textit{at each time step, how many nodes are updated simultaneously?} Two canonical schemes are widely used -- each reflecting a different assumption about the system's clocking.

\subsubsection{Synchronous scheme}

\textbf{Definition}: At each step $t \to t+1$, \textit{all} nodes are updated \textit{simultaneously} based on the same current state $x^{(t)}$:
$$x_i^{(t+1)} = f_i(x^{(t)}) \quad \forall i = 1, \ldots, n$$

The global transition function is $F : \{0,1\}^n \to \{0,1\}^n$ with $F(x) = (f_1(x), \ldots, f_n(x))$.

\textbf{Key properties}:
\begin{itemize}[leftmargin=*]
    \item The function $F$ is \textit{deterministic}: every state has exactly \textit{one} successor.
    \item The STG has \textbf{out-degree 1} at every node.
    \item Because $|\mathcal{X}| = 2^n$ is finite and the trajectory is deterministic, \textit{every} trajectory eventually enters a \textit{cycle} or a \textit{fixed point}.
\end{itemize}

\textbf{Advantages}: Easy to analyse, easy to compute, well-suited to systems with a \textit{common clock} (clock-driven), such as digital logic circuits.

\textbf{Disadvantages}: In biology, the assumption that every gene is updated on the same clock is unrealistic (each gene has its own transcription/translation speed). The synchronous scheme can therefore produce \textit{artifacts} (spurious cycles) that do not exist in the real system.

\subsubsection{Asynchronous scheme}

\textbf{Definition}: At each step $t \to t+1$, \textit{only one} node $j$ is chosen (non-deterministically) and updated; the others keep their values:
$$x_i^{(t+1)} = \begin{cases} f_j(x^{(t)}) & \text{if } i = j \\ x_i^{(t)} & \text{if } i \neq j \end{cases}$$

If $f_j(x^{(t)}) = x_j^{(t)}$, updating $j$ leaves the state unchanged; we only \textit{enumerate the successors that actually differ} from the current state. If \textit{no} node can change the state (i.e.\ $x$ is a fixed-point), we add a self-loop so that the STG remains total.

\textbf{Key properties}:
\begin{itemize}[leftmargin=*]
    \item The transition is a \textbf{one-to-many} relation (non-deterministic): a state may have several successors.
    \item The STG out-degree ranges from 1 (fixed point with self-loop) to $n$.
    \item \textit{Complex attractors} can appear -- terminal SCCs that are not simple cycles.
\end{itemize}

\textbf{Advantages}: Closer to biological reality (each event happens at a different point in time).

\textbf{Disadvantages}: The number of possible transitions is large (up to $2^n \times n$ edges), making the STG hard to visualise once $n > 6$.

\subsection{The State Transition Graph (STG)}\label{subsec:stg}

\subsubsection{Definition}

\begin{quote}
\textit{Given a Boolean Network} $\mathcal{B}$ \textit{and an update scheme} $u \in \{\text{sync}, \text{async}\}$\textit{, the State Transition Graph is the directed graph}
$$G_{\text{STG}}^{(u)} = (\mathcal{X}, E_{\text{STG}}^{(u)})$$
\textit{where:}
\begin{itemize}[leftmargin=*]
    \item The vertices are all $2^n$ states.
    \item An edge $(x, y) \in E_{\text{STG}}^{(u)}$ exists iff $y$ is a valid successor of $x$ under scheme $u$.
\end{itemize}
\end{quote}

The STG is a \textit{complete} representation of the BN dynamics. Every question about the long-term behaviour (attractor, basin) can be answered by analysing the STG.

\subsubsection{Size and representation}

The STG has $2^n$ vertices, which grows exponentially with $n$. Table~\ref{tab:stg-size} shows how rapidly the size explodes.

Advanced libraries (PyBoolNet, GINsim) use symbolic techniques (BDD -- Binary Decision Diagram, AIG) to handle $n > 30$. Within the scope of this project we only implement \textit{explicit enumeration}, which is appropriate up to $n \approx 15$--$18$.

\subsection{Attractors: point, cyclic and complex}\label{subsec:attractor}

\subsubsection{Definition}

\begin{quote}
\textit{An} attractor \textit{of a BN is a set of states} $A \subseteq \mathcal{X}$ \textit{satisfying:}
\begin{enumerate}[leftmargin=*]
    \item \textbf{Forward-invariance}: every successor of every state in $A$ remains in $A$.
    \item \textbf{Strong connectivity}: for every pair $x, y \in A$ there is a path $x \rightsquigarrow y$ in the STG.
    \item \textbf{Minimality}: no proper subset $A' \subsetneq A$ satisfies both (1) and (2).
\end{enumerate}
\end{quote}

Geometrically, an attractor is exactly a \textit{terminal strongly connected component} (terminal SCC) of the STG -- an SCC with no outgoing edges in the condensation graph. Because $\mathcal{X}$ is finite and the STG is total, every trajectory eventually reaches some attractor.

\subsubsection{Classification of attractors}

In the Boolean Network Analyzer, attractors are classified into three kinds:

\begin{enumerate}[leftmargin=*]
    \item \textbf{Fixed-point (steady state)}: $|A| = 1$ and $A = \{x^*\}$ with $F(x^*) = x^*$ (sync) or $f_i(x^*) = x_i^*$ for every $i$ (async). It represents a \textit{stable phenotype} of the system (e.g.\ the G1 state of a cell).
    \item \textbf{Cyclic}: $|A| \geq 2$ and the induced subgraph $G[A]$ is a \textit{simple cycle} -- every node in $A$ has exactly one successor inside $A$. In sync STGs every non-fixed-point attractor is cyclic. It represents \textit{periodic oscillation} (e.g.\ the cell cycle).
    \item \textbf{Complex}: $|A| \geq 2$ and $G[A]$ is not a simple cycle -- at least one node has several successors inside $A$. Only appears in async STGs. It represents a \textit{trapping region} in which the system wanders non-deterministically without ever escaping.
\end{enumerate}

\subsubsection{Basin of attraction}

\begin{quote}
\textit{For an attractor} $A$\textit{:}
\begin{itemize}[leftmargin=*]
    \item The \textbf{weak basin} is the set of states $x \in \mathcal{X}$ from which \textit{at least one} trajectory reaches $A$.
    \item The \textbf{strong basin} is the set of states $x$ from which \textit{every} trajectory must reach $A$ (and no other attractor).
\end{itemize}
\end{quote}

In a sync STG (out-degree 1) the strong basin coincides with the weak basin. In an async STG the strong basin can be a proper subset of the weak basin if multiple attractors exist.

The total size of the weak basins over all attractors may exceed $|\mathcal{X}|$ (when basins overlap), but the total size of the strong basins is exactly $|\mathcal{X}|$ -- they partition the state space.

\subsubsection{Biological and engineering meaning}

According to \textit{Kauffman's hypothesis}, each stable cell phenotype (liver, muscle, neuron, ...) corresponds to a different attractor of the same underlying gene regulatory network. The number of attractors and the size of their basins are therefore directly related to a cell's \textit{differentiation potential} and to its \textit{biological robustness}. In engineering, attractors describe the states the system settles into after a transient -- a digital circuit with unexpected fixed-points may indicate a \textit{stuck-state} bug that needs debugging.

\subsection{In-memory data structures}\label{subsec:data-struct}

\subsubsection{ParsedRule}

\begin{lstlisting}[caption={The \texttt{ParsedRule} data class}, label={lst:parsedrule}]
@dataclass
class ParsedRule:
    target: str                        # name of the updated node
    expression: str                    # original .bnet expression
    python_expression: str             # translated Python expression
    inputs: Tuple[str, ...]            # regulator set (sorted, deduped)
\end{lstlisting}

Design rationale:
\begin{itemize}[leftmargin=*]
    \item The original \texttt{expression} is kept for verbatim display on the UI.
    \item \texttt{python\_expression} allows Python to \texttt{compile} once and \texttt{eval} many times when iterating over $2^n$ states -- much faster than re-parsing a string each time.
    \item \texttt{inputs} is a sorted, deduplicated tuple, making it deterministic and suitable as a cache key.
\end{itemize}

\subsubsection{State}

Each state is a \texttt{Tuple[bool, ...]} of length $n$, ordered according to \texttt{network.nodes}. We use \texttt{tuple} rather than \texttt{list} because:
\begin{itemize}[leftmargin=*]
    \item It is \textit{hashable}, so it can be used as a key in \texttt{dict}/\texttt{set} (required by \texttt{nx.DiGraph}).
    \item It is \textit{immutable}, which avoids accidental mutation when passed around.
\end{itemize}

Each state has two auxiliary representations:
\begin{itemize}[leftmargin=*]
    \item \texttt{dict[str, bool]}: used as the context for \texttt{eval}.
    \item Binary string (e.g.\ \texttt{"101"}): used as a display label.
\end{itemize}

\subsubsection{Graphs: NetworkX DiGraph}

Every graph (influence graph, STG) is represented as a \texttt{networkx.DiGraph} -- the de facto standard Python library for graph analysis. Benefits:
\begin{itemize}[leftmargin=*]
    \item Built-in implementations of \texttt{strongly\_connected\_components}, \texttt{condensation}, \texttt{ancestors}, so we do not have to reimplement Tarjan.
    \item Supports per-node/per-edge attributes (used to store the \texttt{sign} on the influence graph and the \texttt{label} on the STG).
    \item Integrates nicely with \texttt{matplotlib} via \texttt{nx.draw\_networkx\_*}.
\end{itemize}

\subsection{Core algorithms}\label{subsec:algorithms}

\subsubsection{Parser}

The \texttt{.bnet} parser operates in two phases.

\textbf{Phase 1 -- Tokenization}: a linear scan of the expression produces a list of tokens: \texttt{IDENT}, \texttt{(}, \texttt{)}, \texttt{!}, \texttt{\&}, \texttt{|}, \texttt{\&\&}, \texttt{||}, \texttt{0}, \texttt{1}. Whitespace is skipped.

\textbf{Phase 2 -- Translation}: each token is converted to its Python equivalent:

\begin{table}[H]
    \centering
    \renewcommand{\arraystretch}{1.2}
    \begin{tabular}{|c|c|c|c|}
        \hline
        \rowcolor{bklight}
        \textbf{.bnet} & \textbf{Python} & \textbf{.bnet} & \textbf{Python} \\
        \hline
        \texttt{!}/\texttt{not} & \texttt{not} & \texttt{1}/\texttt{True} & \texttt{True} \\
        \hline
        \texttt{\&}/\texttt{\&\&}/\texttt{and} & \texttt{and} & \texttt{0}/\texttt{False} & \texttt{False} \\
        \hline
        \texttt{|}/\texttt{||}/\texttt{or} & \texttt{or} & \texttt{(}, \texttt{)} & \texttt{(}, \texttt{)} \\
        \hline
    \end{tabular}
    \caption{Token translation table: .bnet $\to$ Python}
    \label{tab:token-map}
\end{table}

After Phase 2 the parser calls \texttt{compile(py\_expr, "<bnet>", "eval")} to validate the syntax. Every rule is also \textit{cross-checked}: every variable on the right-hand side must have its own rule (no \textit{dangling input}).

\textbf{Complexity}: $O(L)$ where $L$ is the total length of the expression -- linear.

\textbf{Why this approach}: it is simple and avoids using a parser generator like \texttt{ply} or \texttt{lark}. Because the \texttt{.bnet} grammar is small (four operators), a hand-written tokenizer followed by sequential translation is sufficient and easy to debug.

\subsubsection{Evaluation}

To evaluate the rule $f_v$ on state $x$ we:
\begin{enumerate}[leftmargin=*]
    \item Build the context \texttt{ctx = \{node\_name: bool\_value, ...\}}.
    \item Call \texttt{eval(compiled\_code, \{"\_\_builtins\_\_": \{\}\}, ctx)} -- we pass an empty dict for built-ins to prevent injection.
\end{enumerate}

Compiling the bytecode once in the constructor and reusing it for every \texttt{eval} call in the $2^n$ loop yields a noticeable speed-up over re-parsing the string each time.

\textbf{Complexity}: $O(|f_v|)$ where $|f_v|$ is the AST size. For real biological networks $|f_v| \leq 30$ tokens, so effectively constant.

\subsubsection{Building the influence graph}

The mathematical formulation has been given in \S\ref{subsec:influence-graph}. The implementation is:

\begin{lstlisting}[caption={Edge-sign inference}, label={lst:edge-sign}]
def _infer_edge_sign(self, target, source):
    other = [v for v in rule.inputs if v != source]
    k = len(other)
    increases = decreases = False
    for mask in range(1 << k):
        ctx = {v: bool((mask >> j) & 1) for j, v in enumerate(other)}
        ctx[source] = False
        v_off = eval(code, {"__builtins__": {}}, dict(ctx))
        ctx[source] = True
        v_on = eval(code, {"__builtins__": {}}, dict(ctx))
        if v_off == v_on: continue
        if v_on and not v_off: increases = True
        else: decreases = True
        if increases and decreases: return "?"
    if increases: return "+"
    if decreases: return "-"
    return "?"
\end{lstlisting}

\textbf{Complexity}: $O(2^{k})$ with $k = |\mathrm{In}(v)| - 1$. The total complexity of building the entire influence graph is $O(\sum_v 2^{|\mathrm{In}(v)|-1})$, which is very small in practice.

\subsubsection{Building the STG}

\textbf{Synchronous} (deterministic; each state has exactly one successor):
\begin{enumerate}[leftmargin=*]
    \item Initialise $G$ with the $2^n$ nodes.
    \item For each $x \in \mathcal{X}$: compute $y = F(x)$ and add the edge $x \to y$.
\end{enumerate}

\textbf{Asynchronous} (non-deterministic):
\begin{enumerate}[leftmargin=*]
    \item Initialise $G$ similarly.
    \item For each $x$: compute $y = F(x)$, and let $D = \{i : x_i \neq y_i\}$ be the set of nodes that would change.
    \item If $D = \emptyset$ ($x$ is a fixed point), add the self-loop $x \to x$.
    \item Otherwise, for each $i \in D$ create $x'$ from $x$ by flipping bit $i$ and add the edge $x \to x'$.
\end{enumerate}

\textbf{Complexity}:
\begin{itemize}[leftmargin=*]
    \item Sync: $O(2^n \cdot n)$ (each state needs $n$ rule evaluations).
    \item Async: same order $O(2^n \cdot n)$ because $|D| \leq n$.
\end{itemize}

\textbf{Memory}: $O(2^n)$ nodes plus up to $O(2^n \cdot n)$ edges for async, which becomes the bottleneck when $n \geq 18$.

\textbf{\textit{Reachable-only} mode}: to avoid blowing up memory for larger networks, the UI lets the user turn off \textit{Full state space} and only explore the states reachable from a chosen initial state via BFS. Useful when the user cares about the dynamics from a specific start.

\subsubsection{Finding attractors: SCC + condensation}

\textbf{Reformulation}: an attractor is a terminal SCC of the STG (an SCC with out-degree 0 in the condensation graph).

\textbf{Algorithm}:
\begin{enumerate}[leftmargin=*]
    \item Compute \texttt{sccs = nx.strongly\_connected\_components(g)} -- internally NetworkX implements \textbf{Tarjan's} algorithm (1972) \cite{tarjan1972scc}, complexity $O(V + E)$.
    \item Compute \texttt{cond = nx.condensation(g, scc=sccs)} -- collapses each SCC into a meta-node; the resulting graph is a DAG.
    \item Iterate over \texttt{cond.nodes}: every meta-node with \texttt{out\_degree(cid) == 0} is an attractor.
    \item For each attractor $A$, classify it:
    \begin{itemize}
        \item If $|A| = 1$: \textbf{fixed\_point}.
        \item If every node in $A$ has out-degree $= 1$ inside the subgraph: \textbf{cyclic}.
        \item Otherwise: \textbf{complex}.
    \end{itemize}
\end{enumerate}

\textbf{Why Tarjan?}

\begin{itemize}[leftmargin=*]
    \item \textbf{Optimal complexity} $O(V + E)$ -- no SCC algorithm has better asymptotic.
    \item \textbf{One pass}: a single DFS traversal (Kosaraju needs two passes plus a reversed graph, doubling the memory).
    \item \textbf{Built into NetworkX}: no need to reimplement; lower bug risk.
    \item \textbf{Useful ordering}: Tarjan returns SCCs in reverse topological order of the condensation, which is convenient for iterating over terminal SCCs.
\end{itemize}

\textbf{Kosaraju is also fine?} Yes -- Kosaraju is also $O(V + E)$ and conceptually a little easier (forward DFS then reverse DFS). However Kosaraju needs the reversed graph (an extra $O(V+E)$ memory). With large $V = 2^n$, Tarjan uses less memory.

\subsubsection{Computing the basin of attraction}

For an attractor $A$:
\begin{itemize}[leftmargin=*]
    \item \textbf{Weak basin}: the union of \texttt{nx.ancestors(g, s)} over every $s \in A$, plus $A$ itself. \textbf{Complexity} $O(V + E)$ via reverse BFS.
    \item \textbf{Strong basin} (not fully implemented yet): it would be the weak basin minus all states that also lie in the weak basin of a different attractor.
\end{itemize}

\subsection{User interface design (in-browser web app)}\label{subsec:ui-design}

The UI is a single static page (\texttt{docs/app.html}) served via GitHub Pages. It is intentionally minimal: one sidebar plus five main tabs, no build step and no external JS file beyond the \texttt{vis-network} CDN load.

\begin{itemize}[leftmargin=*]
    \item \textbf{Sidebar}:
    \begin{enumerate}
        \item \textit{Sample network} dropdown -- selects one of the five bundled networks; the source textarea fills in automatically.
        \item \textit{Upload \texttt{.bnet} file} -- standard \texttt{<input type="file">}; read via the FileReader API.
        \item \textit{\texttt{.bnet} source} textarea -- the user can edit the loaded network or paste fresh source.
        \item \textit{Update scheme} segmented control -- Sync/Async.
        \item \textit{STG options} -- toggle full state space vs reachable-only BFS.
        \item \textit{Run} buttons -- \textbf{Analyze} (re-runs the pipeline), \textbf{Download JSON} and \textbf{Download CSV} (exports the results).
    \end{enumerate}
    \item \textbf{Tab 1 -- Influence graph}: rendered with \texttt{vis-network} (force-directed layout); + PNG download button.
    \item \textbf{Tab 2 -- State transition graph}: rendered with \texttt{vis-network}, attractor states highlighted in yellow; + PNG download.
    \item \textbf{Tab 3 -- Attractors}: collapsible cards listing every attractor with kind (fixed-point/cyclic/complex), state members, weak-basin size.
    \item \textbf{Tab 4 -- Simulate}: pick an initial state with checkboxes, then step forward (single step or batch of 20). Trajectory shown as a table.
    \item \textbf{Tab 5 -- Rules}: read-only view of the parsed rules.
\end{itemize}

\textbf{Reactivity}: the entire pipeline is re-run on every change to the source, scheme or STG-mode toggle. Because the engine is fully in-memory and small networks run in $< 100$\,ms, no caching is needed. For larger networks, the user can disable \textit{full state space} to fall back to reachable-only BFS from the all-zero state.

\textbf{Deployment}: pushing to the \texttt{main} branch triggers \texttt{.github/workflows/pages.yml}, which publishes \texttt{docs/} to GitHub Pages. The current live demo URL is \url{https://dangkhoi-dev.github.io/boolean-network-analyzer/}.

\subsection{Methodology summary}\label{subsec:method-summary}

The software follows four design principles:
\begin{enumerate}[leftmargin=*]
    \item \textbf{Separation of concerns}: the in-browser JS engine and the Python reference engine are fully decoupled and live in different directories.
    \item \textbf{Lean dependencies}: zero Python deps for the actual user interface (it is a static HTML/JS page); only five lightweight Python deps (NetworkX, matplotlib, pandas, numpy, pytest) for the reference engine, CLI and test suite.
    \item \textbf{Testability}: every engine function can be tested in isolation with \texttt{pytest}.
    \item \textbf{Pythonic and readable}: each function is under 50 lines and has full docstrings and type hints, in line with the Professionalism criterion of the rubric.
    \item \textbf{Zero-install distribution}: the primary user interface ships as a single static HTML page on GitHub Pages; nothing to install for end users.
\end{enumerate}

\subsubsection{Test case 1: \texttt{toy\_switch} (3 nodes)}

\textbf{Rules}: \texttt{A,!B/B,A\&!C/C,B}.

\textbf{Influence graph} (see Figure~\ref{fig:influence-toy}): four edges -- $B \to A(-)$, $A \to B(+)$, $C \to B(-)$, $B \to C(+)$. There is one short negative feedback loop $A \leftrightarrow B$.

\textbf{Synchronous STG}: 8 states, 8 edges (every state has out-degree 1). The analyzer identifies \textbf{one cyclic attractor} -- let us inspect this carefully by hand.

\textbf{Manual verification}: at the candidate fixed-point \texttt{100} we compute $f_A = \lnot 0 = 1$, $f_B = 1 \land \lnot 0 = 1$. Therefore $f_B = 1$, and \texttt{100} is \textit{not} a fixed point. The full transition table is:

Every other state (\texttt{000, 010, 101, 111}) is transient and leads into the cycle. This is a valuable example: even a 3-node network can produce non-trivial dynamics, and the analyzer must compute them correctly. Our Boolean Network Analyzer returns \textit{1 cyclic attractor of size 4: \{001, 011, 100, 110\}} -- matching the manual analysis.

\subsubsection{Test case 2: \texttt{bistable\_toggle} (2 nodes)}

\textbf{Rules}: \texttt{A,!B/B,!A}.

\textbf{Influence graph}: $A \xrightarrow{-} B$, $B \xrightarrow{-} A$ -- one positive feedback loop (two negative edges).

\textbf{Thomas's theorem prediction}: the presence of a positive loop $\Rightarrow$ the network may exhibit multistability. Theory predicts \textit{two fixed-point attractors} \texttt{10} and \texttt{01}.

\textbf{Synchronous STG}: four states, four edges.
\begin{itemize}[leftmargin=*]
    \item \texttt{00} $\to$ \texttt{11}: both turn on.
    \item \texttt{11} $\to$ \texttt{00}: both turn off.
    \item \texttt{01} $\to$ \texttt{01}: $A = \lnot 1 = 0$, $B = \lnot 0 = 1$ $\Rightarrow$ fixed.
    \item \texttt{10} $\to$ \texttt{10}: by symmetry, fixed.
\end{itemize}

\textbf{Synchronous result}: 2 fixed-points (\texttt{10}, \texttt{01}) plus one 2-cycle (\texttt{00} $\leftrightarrow$ \texttt{11}). \textit{The 2-cycle is a sync artifact}.

\textbf{Asynchronous result}: exactly 2 fixed points, with no 2-cycle (because async never updates both nodes at once). See Figure~\ref{fig:stg-async-bistable}.

\textbf{Cross-validation against PyBoolNet}: running the equivalent \texttt{PyBoolNet.attractors.compute\_attractors(...)} on \texttt{bistable\_toggle.bnet} returns the same 2 fixed points under async, and 2 fixed points plus a 2-cycle under sync. \textbf{100\% agreement}.

\subsubsection{Test case 3: \texttt{repressilator} (3 nodes)}

\textbf{Rules}: \texttt{A,!C/B,!A/C,!B}.

\textbf{Influence graph}: three negative edges forming a cycle $A \to B \to C \to A$ -- a single negative feedback loop, so we expect oscillation.

\textbf{Synchronous STG}: 8 states. Theory predicts a 6-cycle representing the oscillation (\texttt{100 $\to$ 110 $\to$ 010 $\to$ 011 $\to$ 001 $\to$ 101 $\to$ 100}) plus a 2-cycle (\texttt{000} $\leftrightarrow$ \texttt{111}). The analyzer returns \textit{1 cyclic attractor of size 6 plus 1 cyclic attractor of size 2}. Together: eight states accounted for -- match.

\textbf{Asynchronous STG}: more involved. Because every non-fixed-point state has multiple successors, the result is \textit{a single complex attractor} that covers most of the state space; it qualitatively still represents oscillation. No fixed points.

\textbf{Cross-validation against PyBoolNet}: full agreement.

\subsubsection{Test case 4: \texttt{fission\_yeast} (9 nodes)}

\textbf{Rules}: nine nodes named \texttt{SK, Cdc2\_Cdc13, Ste9, Rum1, Slp1, Cdc2\_Cdc13\_active, Wee1\_Mik1, Cdc25, Start}.

\textbf{State space}: $2^9 = 512$ states. The analyzer builds the synchronous STG in \textbf{about 0.5 seconds}.

\textbf{Synchronous result}: \textbf{1 cyclic attractor of size 2}. The original paper expects a single dominant fixed point representing the G1 state; however, in this reduced version the node \texttt{Start} has the rule \texttt{!Start} that forces oscillation, so the attractor is actually a 2-cycle between two variants of G1 differing only on the \texttt{Start} variable. To recover the canonical G1 fixed point one must \textit{clamp} the input \texttt{Start} to 1 (modelling external stimulation); the STG then reduces to 256 states and the expected single fixed point appears.

\textbf{Observation}: the analyzer lets the user provide a clamped \texttt{.bnet} file to model this case. This is a nice illustration of the value of a flexible input pipeline.

\textbf{Cross-validation against PyBoolNet} on the same file (unclamped): both return the same 2-cycle. Match.

\subsubsection{Test case 5: \texttt{mammalian\_cell\_cycle} (10 nodes)}

\textbf{Rules}: ten nodes modelling the mammalian cell-cycle network.

\textbf{State space}: $2^{10} = 1\,024$.

\textbf{Asynchronous result}: per Faure \emph{et al.} 2006, when \texttt{CycD} $= 1$ (division stimulus) the network exhibits \textit{a single complex attractor} representing the cell cycle. When \texttt{CycD} $= 0$ there is a fixed point representing G0 (quiescence).

\textbf{Our analyzer returns}: one complex attractor in the \texttt{CycD=1} subspace, one fixed point in the \texttt{CycD=0} subspace. Matches the paper.

\textbf{Timing}: sync $\sim 1$\,s, async $\sim 4$\,s (each state has up to 10 successors).

\subsection{Bugs found and fixed during development}\label{subsec:bugs}

The implementation process surfaced several bugs worth recording:

\begin{enumerate}[leftmargin=*]
    \item \textbf{Bug \#1 -- Reserved words \texttt{and/or/not}}: the first version of the parser did not reject variable names that collide with Python keywords. As a result, the rule \texttt{or, !and} parsed successfully but \texttt{eval} raised a SyntaxError. Fix: add a \texttt{\_RESERVED} set and reject those identifiers.
    \item \textbf{Bug \#2 -- Async without a self-loop}: an early version of \texttt{asynchronous\_successors} returned an empty list at fixed points, so Tarjan saw an isolated sink and produced no SCC. Consequence: fixed points were missed in async attractors. Fix: return \texttt{[state]} (self-loop) when no diff is found.
    \item \textbf{Bug \#3 -- Influence sign for non-monotonic rules}: a rule such as \texttt{f = A xor B} (not in the initial tests) caused the \texttt{?} sign to be omitted because the \texttt{increases and decreases} check did not short-circuit correctly. Fix: add an early \texttt{return}.
    \item \textbf{Bug \#4 -- Tarjan stack overflow in the JS engine}: the first version used a recursive Tarjan implementation; running it on a $2^{16}$-state STG hit the JS engine's call-stack limit and threw \texttt{RangeError: Maximum call stack size exceeded}. Fix: rewrite Tarjan as an explicit-stack iterative version. After the fix, networks up to $n = 16$ analyse without blowing the stack.
\end{enumerate}

    \item 23/23 \texttt{pytest} cases pass.

\subsection{Limitations}\label{subsec:limitations}

I openly acknowledge some limitations:

\begin{enumerate}[leftmargin=*]
    \item \textbf{State explosion for $n > 16$}: building the full STG becomes impractical. The current version does not yet support BDD or AIG backends.
    \item \textbf{Slow UI when rendering STGs with $> 1024$ nodes}: \texttt{matplotlib} layout is slow; at $n = 12$ (4\,096 nodes) drawing already takes more than 15 seconds and the figure is barely readable.
    \item \textbf{No multi-valued network (MDD) support}: only Boolean (two-state) networks are handled. Real biological models sometimes require 3--4 levels (e.g.\ low/medium/high).
    \item \textbf{No probabilistic updates}: every update is deterministic (sync) or uniformly non-deterministic (async). Probabilistic Boolean Networks (PBNs) are not supported.
    \item \textbf{No strong basin}: only weak basins are computed.
    \item \textbf{No persistent cache}: each time the page is reloaded the STG has to be rebuilt from scratch. Using \texttt{localStorage} or IndexedDB to cache the last analysis would shave a few hundred milliseconds on warm reloads.
\end{enumerate}

\subsection{Future work}\label{subsec:future}

Worthwhile extensions include:

\begin{enumerate}[leftmargin=*]
    \item \textbf{Add a BDD/AIG backend} (via \texttt{pyeda} or by calling PyBoolNet) to scale to $n \geq 50$.
    \item \textbf{Render the STG with D3 or Plotly} instead of matplotlib: interactive zoom/pan, click on a node to expand.
    \item \textbf{Multi-valued networks} (MDD): extend the parser and engine to support values $\{0, 1, 2, \ldots, k\}$; replace Boolean functions with Multi-valued Decision Diagrams.
    \item \textbf{Probabilistic Boolean Networks} (PBN): allow each node to carry a list of rules with associated probabilities; analyse the resulting Markov chain on the STG.
    \item \textbf{Control-kernel analysis}: identify the minimum set of nodes whose values must be clamped to steer the system into a desired attractor (used in drug-target identification).
    \item \textbf{Generate \texttt{.bnet} from the UI}: let the user create the network through a form instead of typing the file by hand.
    \item \textbf{Automatic PDF report generation}: after analysis, produce a PDF summary with the influence graph, the STG and the attractor table.
    \item \textbf{Collaborative editing}: multiple users editing the same \texttt{.bnet} on the web via WebSockets.
\end{enumerate}
